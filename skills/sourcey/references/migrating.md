# Migrating to Sourcey

`sourcey migrate <framework> [root]` converts a documentation project once. Afterwards the project is ordinary Sourcey: nothing reads the old framework's configuration again. Every page keeps its URL and every heading keeps its anchor; the migration verifies both in a temporary build before it writes anything.

## Before you run it

- Commit or stash work in progress, so the migration's diff is the only change to review.
- Docusaurus configuration is a program: run `npm install` first and run the migration in the environment the production build uses (its `.env`, locale variables), because it loads `docusaurus.config.*` as Docusaurus does.
- A Mintlify project still on `mint.json` upgrades to `docs.json` with Mintlify's own CLI first.
- Always `--dry-run` first and read the whole report.

## What each converter does

| Framework | Carries over | Stops on |
| --- | --- | --- |
| Docusaurus | Docs instances as tabs at the same routes, versions, translations, sidebars (autogenerated included), `_category_.json`, admonitions, Tabs, DocCardList, CodeBlock, ThemedImage, Link, partials, static page JavaScript (exports, imported data, `.map()` lists, the page's own components and helpers), client redirects, `src/pages/*.md` as site pages, navbar links and dropdowns, footer links, colours | React pages, your own React components (until mapped), API reference plugins, tag pages, content MDX 3 cannot read |
| MkDocs | `nav` or the default navigation, Material tabs and collapsed sections, admonitions, details, tabbed, snippets, `attr_list` heading IDs, redirects, copyright and Material's social links, palette and fonts | Plugins that generate content (`macros`, `awesome-pages`, `mkdocstrings`, `i18n`, `blog` and similar), a custom `toc` slugify, maths, invalid frontmatter |
| Mintlify | `docs.json` navigation (tabs, groups, anchors as sidebar sections), most components as written, snippets as includes, API pages as a native reference with an overlay, routes, navigation and fragment aliases | Several OpenAPI documents, a group that generates every operation's page, versions and languages, components with no native form, your own `/snippets/*.jsx` (until mapped) |
| Astro | Starlight config, sidebar, locales, asides, components and `starlight-openapi`; custom documentation routes and collections declared in the mapping file. The docs stay mounted in the Astro site through `sourcey/astro` | Components without a mapping |

Footer links that only repeat the navbar or point at the docs' own pages, which the sidebar lists, are left out and named in the report.

## The mapping file

Decisions that live in the project's code are made once, in a module passed with `--mapping`:

```ts
export default {
  // Your components, by module and export, as native components or Markdown.
  components: {
    "./src/components/Callout.tsx": {
      Callout: ({ props }) => ({ component: props.type === "warning" ? "Warning" : "Info", props: { title: props.title ?? "Note" } }),
    },
  },
  // Native components you wrote for your own widgets, registered by name.
  definitions: { ConfigOptions: "sourcey/components/config-options.ts" },
};
```

A mapping returns a native component, Markdown, a fenced block, or an error with a reason. It is read only during the migration and never becomes part of the config.

## After the migration

1. Read the review notes and act on each: styling that did not carry over, a component that became a plain link, an option that has no native form.
2. Add `sourcey` to the project's dependencies and remove the old framework once nothing else uses it.
3. Build and compare the new site with the old one, side by side, for every page type (home, a guide, a reference page, the 404 page), on desktop and on a phone. The migration has already checked routes, anchors, text and images; your review is for how it reads ([design-review.md](design-review.md)).
4. Keep the converter's output (`sourcey.config.ts`) as the record of what was converted. When the project wants more, such as an API or MCP reference beside the guides, rename it (`sourcey.converted.ts`), import it into a new `sourcey.config.ts` and add to it there:

```ts
import converted from "./sourcey.converted.ts";
import { defineConfig, openapi } from "sourcey";

export default defineConfig({
  ...converted,
  navigation: { tabs: [...converted.navigation.tabs, { tab: "API Reference", slug: "api", source: openapi("./openapi.json") }] },
});
```

Running the migration again on a migrated project proposes no changes.
