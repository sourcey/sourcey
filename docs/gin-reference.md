## What the reference says about the project (maintainer-facing findings)

These are findings from reading the pinned commit *through the generated reference*.
Each names the file and line in the pinned tree.

1. **The RFC 10008 `QUERY` method is in the code but not in the README.** The pinned
   commit is the `QUERY` support change itself (`routergroup.go:14-17` declares
   `MethodQuery`, `routergroup.go:176` adds `(*RouterGroup).QUERY`), yet
   `grep -ic query README.md` returns **0** at this commit. A reader who learns
   about `QUERY` from this reference has no path from the README to it.
2. **`MethodQuery` is a hand-rolled shim that needs a migration note.** The constant
   duplicates a stdlib symbol the comment itself predicts will arrive
   (`golang/go#71459` tracks the proposal). When `net/http` ships `http.MethodQuery`,
   two sources of truth for the same method name can drift.
3. **Four exported entry points have no doc comment at all**, measured over the 431
   exported entries in the snapshot: `type ContextKeyType int` (`context.go:52`),
   `(*gin.Engine).Handler` (`gin.go:257`), `type SliceValidationError []error`
   (`binding/default_validator.go:21`) and `binding.MapFormWithTag`
   (`binding/form_mapping.go:40`). The last one is the costly omission: it is
   exported precisely so that users can call it.
4. **`(*gin.Context).BindWith` is deprecated but still exported and documented**, so
   it reads as a supported API next to the replacement.
